MODULE 04 / SSH KEY GUARD

SSH Key Guard

Monitoring SSH keys of Linux server users.

SSH Key Guard — a ServerGuard component that watches the SSH keys of Linux server users. It detects the addition and removal of keys in authorized_keys and stores a detailed event.
Module version 1.0.1
Platform Linux
Language Python 3
Primary object ~/.ssh/authorized_keys

1. Why SSH Key Guard is needed

The authorized_keys file determines which public keys can sign in to the server as a specific user:

/home/<user>/.ssh/authorized_keys
/root/.ssh/authorized_keys

If someone else's key is added to it without your knowledge, that is a hidden way to sign in: it will keep working even after the password is changed. SSH Key Guard lets you quickly notice such a change.

detect a change → identify the key → record an event

2. Key features

  • monitoring of authorized_keys for all users;
  • detection of added and removed keys;
  • baseline — a reference set of keys;
  • fingerprint SHA256:... for convenient key identification;
  • integration with Linux Audit (auditd): process, user, command;
  • network information and GeoIP for public IPs;
  • structured JSON events and local history;
  • operation as a systemd service;
  • a simple command interface.

3. How it works

The module combines two mechanisms:

Snapshot monitoring   — what changed?
Linux Audit           — which operation and which process did it?

authorized_keys
       |
       v
   snapshot
       |
       v
  comparison with the previous state
       |
  +----+-----------+
  |                |
  v                v
key_added      key_removed
  |                |
  +-------+--------+
          |
          v
   creating an event
          |
          v
    JSON log

4. Baseline

Before monitoring, a baseline is created — a list of keys that are considered known.

baseline:   KEY-A, KEY-B
later:      KEY-A, KEY-B, KEY-C
result:     KEY-C → new key (key_added)

Create a baseline manually:

python3 ssh_key_guard.py init

5. Events

Event Meaning
key_added A new SSH key detected
key_removed A previously known key is no longer found

Example: there was KEY-A, now there is KEY-A, KEY-B — a key_added is created for KEY-B.

6. What is stored about a key

{
  "type": "ssh-ed25519",
  "fingerprint": "SHA256:...",
  "comment": "admin@computer",
  "line": 3
}

Common types are supported: ssh-rsa, ssh-ed25519, ecdsa-sha2-nistp256/384/521, as well as security-key and certificate variants of OpenSSH.

Fingerprint allows a key to be identified without showing it in full.

7. User and file information

The event is associated with the account whose authorized_keys was changed:

{ "username": "admin", "uid": 1000, "home": "/home/admin", "shell": "/bin/bash" }

The file path and its metadata (size, permissions, modification time, SHA-256) are also stored.

8. Linux Audit

If auditd is installed on the server, SSH Key Guard receives additional context about the operation:

UID, AUID, PID, PPID
process name and executable file
command and working directory
operation result, terminal

For example: the key was added by a vim process of a user with UID 1000, or by a python3 script.

AUID preserves the original user even after sudo or su — this helps to understand exactly who performed the action.

sshd → bash → sudo → vim

9. Operation without auditd

Without auditd, the module continues to detect changes by comparing snapshots: which key was added or removed and which user was affected. Only the details about the process and operation will be missing, so for the full picture auditd is recommended.

10. Network information and GeoIP

The module can determine the IP address associated with the SSH session (from audit or the active session).

For public IPs, the external service ipinfo.io is used: country, region, city, organization, hostname. For local and private addresses, no request is made.

GeoIP does not determine a person's physical location. Use it as an additional hint. Keep in mind that the public IP is transmitted to a third-party service.

11. Data storage

  • Events — the ssh_key_events.json log, up to the last 5000 events;
  • State — the current known state for comparison.

Writes are performed through a temporary file followed by replacement, so an abnormal termination should not corrupt the log.

Each event has a unique ID:

{
  "id": "...", "version": "1.0.1", "timestamp": "...",
  "action": "key_added",
  "account": {}, "file": {}, "key": {}, "old_key": null,
  "modifier": {}, "network": {}, "server": {}
}

12. Launch and check interval

By default, the check is performed every 5 seconds:

python3 ssh_key_guard.py monitor

A different interval:

python3 ssh_key_guard.py monitor --interval 10

For continuous operation, the module is launched as a systemd service and starts automatically after the server reboots.

13. Commands

Command Purpose
monitor Continuous monitoring
monitor --interval N Monitoring with an interval of N seconds
init Creating a baseline
scan One-time scan
events Recent events
events N Last N events
audit Linux Audit check
audit-remove Removing ServerGuard audit rules
version Module version

14. systemd service

systemctl status serverguard-ssh-key.service
systemctl start serverguard-ssh-key.service
systemctl stop serverguard-ssh-key.service
systemctl restart serverguard-ssh-key.service

Service log:

journalctl -u serverguard-ssh-key.service -n 50
journalctl -u serverguard-ssh-key.service -f

15. Requirements and permissions

Linux, Python 3, and OpenSSH are required. For extended auditing, auditd, auditctl, and ausearch are recommended; for network information, ss and curl are used.

Some functions require administrator permissions: reading other users' files, working with auditd, analyzing processes. Therefore, continuous monitoring is usually run as root.

16. Privacy

Events may contain the username, UID, the path to authorized_keys, fingerprint, IP address, command, and process information. This is sensitive data: restrict access to the logs and state files to trusted administrators only.

17. What SSH Key Guard does not do

This is a system for monitoring, detection, auditing, and logging. It does not:

  • remove suspicious keys;
  • block IP addresses;
  • delete users or change passwords;
  • stop the SSH server;
  • replace a firewall or brute-force protection.

The decision on further actions is made by the administrator or other security components.

SSH Key Guard Firewall Brute-force protection
What it controls Keys in authorized_keys Connections, ports, IP Failed login attempts

18. Limitations

  • The module analyzes recognized SSH keys, so changing only a comment does not always create an event.
  • The check is periodic: a change that was reverted between two checks may not make it into the snapshot. auditd reduces this risk.
  • Unavailability of GeoIP or another additional source does not stop the main monitoring.

19. Recommendations

  • create the baseline on a known-clean server;
  • install and use auditd;
  • do not modify the state files manually;
  • restrict access to the logs;
  • monitor the state of the systemd service;
  • regularly review events and check unfamiliar keys;
  • use SSH Key Guard together with SSH Hardening, Security, and FileGuard.

20. Conclusion

identifies users → finds authorized_keys → creates a baseline
→ compares snapshots → detects added and removed keys
→ adds context from auditd → stores a structured event

SSH Key Guard is responsible for a distinct security layer — control of SSH keys and the events related to them.

This documentation describes the purpose and operating principle of SSH Key Guard at the user level.
