MODULE 03 / SSH HARDENING

SSH Hardening

Review and manage SSH configuration.

Module: SSH Hardening
Main file: ssh_hardening.py
Platform: Linux / Ubuntu
Language: Python 3
Technologies: Python, OpenSSH, systemd
Project: ServerGuard

Purpose of the module:

Automated hardening of SSH server security,
OpenSSH configuration verification, backup,
application of a controlled security policy
and safe restoration of the SSH configuration.

1. GENERAL DESCRIPTION

SSH Hardening is a server module of ServerGuard designed for automatic management of OpenSSH security settings.

The module allows you to:

  • check user privileges;
  • determine the SSH service;
  • check SSH status;
  • create the required directories;
  • create a backup of the configuration;
  • create the ServerGuard configuration;
  • verify the OpenSSH configuration;
  • apply the changes;
  • reload the SSH service;
  • verify the parameters actually applied;
  • determine the hardening state;
  • remove the ServerGuard configuration;
  • restore the previous configuration;
  • perform a rollback on error.

The main idea of the module:

ServerGuard does not modify the entire /etc/ssh/sshd_config.

Instead, a separate configuration fragment is used:

/etc/ssh/sshd_config.d/99-serverguard-hardening.conf

The main file:

/etc/ssh/sshd_config

while remaining separate.

This approach allows ServerGuard to apply its own SSH policy without completely rewriting the administrator's existing configuration.

2. WHAT SSH HARDENING IS

Hardening is the strengthening of system security by restricting unnecessary or potentially dangerous capabilities.

In the context of SSH, this means changing the OpenSSH policy so that the server allows only the necessary features.

ServerGuard sets the following parameters:

PermitEmptyPasswords no

X11Forwarding no

AllowTcpForwarding no

AllowAgentForwarding no

MaxAuthTries 3

LoginGraceTime 30

Compression no

PermitRootLogin prohibit-password

This restricts:

  • empty passwords;
  • root password authentication;
  • the number of authentication attempts;
  • the authentication time;
  • X11 forwarding;
  • TCP forwarding;
  • SSH Agent Forwarding;
  • SSH compression.

3. SSH HARDENING IS NOT BRUTE-FORCE PROTECTION

It is important to separate the two tasks.

SSH Hardening is responsible for:

SSH POLICY

That is:

which capabilities are allowed;
which capabilities are prohibited;
which restrictions are applied.

The Security module is responsible for:

ATTACK DETECTION

For example:

  • analysis of failed logins;
  • detection of a large number of attempts;
  • IP analysis;
  • IP blocking;
  • brute-force protection.

Therefore:

SSH Hardening
    =
OpenSSH configuration hardening

and:

Security
    =
detection and blocking of suspicious activity.

These mechanisms complement each other.

11. SSH SERVICE CHECK

The function:

The following is used:

If the result is:

Example:

SSH service: ACTIVE

If the service is inactive, its state is displayed to the user.

12. BACKUP

Modifying the SSH configuration is a potentially dangerous operation.

An error in the configuration can cause new SSH connections to be unable to establish.

Therefore, ServerGuard uses the principle:

BACKUP BEFORE CHANGE

Before changing the configuration, a backup is created.

The backup is located at:

/opt/serverguard/backups

13. BACKUP OF THE MAIN CONFIGURATION

backup_main_config()

/etc/ssh/sshd_config

A file is created:

sshd_config_YYYYMMDD_HHMMSS.backup

For example:

sshd_config_20260930_215300.backup

Copying uses:

shutil.copy2()

The timestamp allows multiple backups to be stored.

14. BACKUP OF THE SERVERGUARD CONFIGURATION

If the following already exists:

/etc/ssh/sshd_config.d/99-serverguard-hardening.conf

Example:

99-serverguard-hardening_20260930_215300.backup

This way, the previous version of the ServerGuard policy can be preserved.

Important:

the main sshd_config

and:

ServerGuard hardening config

are backed up separately.

15. CREATING THE HARDENING CONFIGURATION

The function:

The ServerGuard policy is written to the file.

Main parameters:

PermitEmptyPasswords no

X11Forwarding no

AllowTcpForwarding no

AllowAgentForwarding no

MaxAuthTries 3

LoginGraceTime 30

Compression no

PermitRootLogin prohibit-password

After creation, the permissions are set:

0644

16. PermitEmptyPasswords

The parameter:

PermitEmptyPasswords no

prohibits the use of an empty password during SSH authentication.

The idea of the setting:

empty password
    |
    v
SSH authentication
    |
    v
prohibited

This eliminates the possibility of using an empty password as an SSH authentication mechanism.

17. X11Forwarding

ServerGuard sets:

X11Forwarding no

X11 Forwarding allows X11 graphics to be transmitted over SSH.

If the server is used primarily for:

  • server applications;
  • administration;
  • development;
  • background services;

X11 forwarding may not be needed.

Therefore, ServerGuard disables this capability.

Important:

SSH is NOT disabled by this.

Only X11 forwarding is disabled.

18. AllowTcpForwarding

ServerGuard sets:

AllowTcpForwarding no

TCP forwarding allows SSH to be used for network tunneling.

For example:

client
   |
   | SSH
   v
server
   |
   v
another network resource

If the server uses SSH tunnels, disabling TCP forwarding may change the existing workflow.

Therefore, this setting must be taken into account before applying hardening.

19. AllowAgentForwarding

ServerGuard sets:

AllowAgentForwarding no

SSH Agent Forwarding allows the SSH agent to be used over a remote connection.

This can be convenient when administering multiple servers.

If the server does not require this capability, ServerGuard disables it.

20. MaxAuthTries

ServerGuard sets:

MaxAuthTries 3

The parameter limits the number of authentication attempts within a single SSH connection.

Important:

MaxAuthTries 3

does not mean:

"the IP is blocked after three attempts".

These are different mechanisms.

IP blocking belongs to the separate Security system.

21. LoginGraceTime

ServerGuard sets:

LoginGraceTime 30

The client is given a limited time to complete authentication.

In the ServerGuard policy:

30 seconds

This reduces the lifetime of an unauthenticated connection.

22. Compression

ServerGuard sets:

Compression no

SSH compression is disabled.

This reduces the number of available SSH features if compression is not required by a particular server.

23. PermitRootLogin

ServerGuard sets:

PermitRootLogin prohibit-password

This means that root password authentication over SSH is prohibited.

At the same time, root key authentication may remain available if other OpenSSH settings allow it.

Thus:

root + password
    |
    v
prohibited

root + SSH key
    |
    v
may be allowed

This differs from:

PermitRootLogin no

With:

PermitRootLogin no

root is completely prohibited over SSH.

24. WHY prohibit-password IS USED

ServerGuard intentionally uses:

PermitRootLogin prohibit-password

rather than:

PermitRootLogin no

This preserves the possibility of administrative access via an SSH key.

The final login capability still depends on other OpenSSH parameters.

For example:

PubkeyAuthentication
PasswordAuthentication
AuthorizedKeysFile

and other settings.

Therefore, the final state is recommended to be verified via:

sshd -T

25. CONFIGURATION VERIFICATION

Before reload, ServerGuard uses:

sshd -t

The command checks the OpenSSH configuration for errors.

Conditionally:

sshd -t
   |
   +---- 0
   |      |
   |      v
   |   VALID
   |
   +---- != 0
          |
          v
       INVALID

If the configuration is invalid, the apply operation must not continue as successful.

26. WHY sshd -t IS IMPORTANT

Imagine:

ServerGuard
     |
     v
 creates config
     |
     v
   sshd -t
     |
   +---+
   |   |
  OK ERROR
   |   |
   v   v
 reload rollback

Thus, a syntax error is detected before the configuration is actually applied.

27. RELOAD SSH

After a successful check, the following is executed:

systemctl reload <ssh-service>

The following is used:

reload

rather than the mandatory:

restart

This allows the running SSH daemon to reread the configuration.

On a successful reload, the module continues with verification.

28. EFFECTIVE CONFIGURATION

After applying, the following is used:

sshd -T

The command shows the effective OpenSSH configuration.

This is especially important because OpenSSH may use multiple configuration files.

For example:

/etc/ssh/sshd_config

and:

/etc/ssh/sshd_config.d/*.conf

Therefore, the contents of a single file do not always equal the final SSH daemon configuration.

ServerGuard checks specifically the result of:

sshd -T

29. RETRIEVING VALUES

The function:

get_config_value(config, name)

retrieves the value of a parameter from the result of:

sshd -T

For example:

permitrootlogin prohibit-password

is parsed as:

name:
    permitrootlogin

value:
    prohibit-password

The comparison is performed case-insensitively.

If the parameter is missing:

unknown

30. VALUE COMPARISON

The function:

value_matches(actual, expected)

compares:

the actual value

and:

the expected value.

For:

prohibit-password

the following may also be taken into account:

without-password

This is due to differences in how this setting is represented across OpenSSH versions.

31. HARDENING CHECK

The main function:

check_hardening()

first checks:

/etc/ssh/sshd_config.d/99-serverguard-hardening.conf

If the file does not exist:

If the file exists, the following is executed:

sshd -T

After that, the parameters are checked.

34. INFORMATIONAL PARAMETERS

For:

That is, these parameters are shown to the user but are not used as a strict condition for successful hardening.

For example:

35. CHECK RESULT

If all required parameters match the policy:

If at least one required parameter differs:

This allows distinguishing between:

the file exists

and:

the policy is actually applied.

If the file does not exist, this is not considered a critical error.

Removal is used, in particular, during rollback.

It is needed to enable rollback if the selected old configuration turns out to be invalid.

47. PROTECTION AGAINST PATH TRAVERSAL

The command:

/tmp/file

..\file

Goal:

This is protection against Path Traversal.

60. MODULE SECURITY

The module implements several protective mechanisms.

1. ROOT CHECK

Only root can perform privileged operations.

2. BACKUP BEFORE CHANGE

A backup is created before any change.

3. CONFIG VALIDATION

The following is used:

sshd -t

4. EFFECTIVE CONFIG CHECK

The following is used:

sshd -T

5. EMERGENCY BACKUP

Before restore, the current configuration is saved.

6. ROLLBACK

If there is a problem with restoration, the emergency backup is used.

7. PATH TRAVERSAL PROTECTION

Dangerous path elements are prohibited.

8. BACKUP TYPE VALIDATION

Only the provided backup types are allowed.

61. WHAT EXACTLY SSH HARDENING PROTECTS

The module changes the OpenSSH policy.

It restricts:

  • empty passwords;
  • root password login;
  • the number of authentication attempts;
  • authentication time;
  • X11 forwarding;
  • TCP forwarding;
  • SSH Agent Forwarding;
  • SSH compression.

This is protection specifically at the level of:

SSH daemon configuration.

62. WHAT THE MODULE DOES NOT DO

SSH Hardening is NOT:

  • an antivirus;
  • a firewall;
  • IDS/IPS;
  • an IP blocking system;
  • a network packet analysis system;
  • a file monitoring system;
  • a malware detection system;
  • a full-fledged DDoS protection.

It is responsible for the OpenSSH configuration.

For example:

MaxAuthTries 3

does not mean:

"the IP will be blocked after three attempts".

A separate ServerGuard Security logic is used for IP detection and blocking.

63. SSH HARDENING AND SECURITY

The ServerGuard architecture separates responsibilities.

SSH Hardening:

OpenSSH configuration
      |
      +-- authentication limits
      +-- root login policy
      +-- forwarding
      +-- compression
      +-- empty passwords

Security:

SSH activity
      |
      +-- failed login detection
      +-- IP analysis
      +-- brute-force detection
      +-- blocking

One module does not replace the other.

67. WHY A CONFIGURATION FRAGMENT IS USED

Instead of fully modifying:

/etc/ssh/sshd_config

ServerGuard creates:

/etc/ssh/sshd_config.d/99-serverguard-hardening.conf

The advantage of this approach:

the main configuration file remains separate;

the ServerGuard policy has its own file;

updating ServerGuard does not require completely rewriting
the administrator's configuration;

rollback of the ServerGuard configuration can be performed separately.

68. WHY sshd -t IS USED

The command:

sshd -t

is a barrier before reload.

Conditionally:

sshd -t
   |
   +-- 0
   |    |
   |    v
   |  VALID
   |
   +-- != 0
        |
        v
      ERROR

Without this check, an incorrect configuration could be applied without the error being detected in advance.

69. WHY sshd -T IS USED

The command:

sshd -T

shows the resulting OpenSSH configuration.

This is especially important when the following are present:

/etc/ssh/sshd_config

and:

/etc/ssh/sshd_config.d/*.conf

ServerGuard checks not merely the created file but the resulting state that OpenSSH sees.

70. EFFECTIVE CONFIGURATION

Two concepts can be distinguished.

CONFIGURATION FILE:

99-serverguard-hardening.conf

and:

EFFECTIVE CONFIGURATION:

the result of sshd -T

The first shows:

what ServerGuard wrote.

The second shows:

what OpenSSH actually uses.

Therefore:

the file exists

does not necessarily mean:

the parameter is actually applied.

74. IMPORTANT FEATURE OF RESTORE

Restoring the main configuration modifies:

But the ServerGuard hardening is located separately:

/etc/ssh/sshd_config.d/99-serverguard-hardening.conf

Therefore:

restore sshd_config

does not automatically mean:

After restoration, the resulting configuration should be verified via:

sshd -T

or:

python3 ssh_hardening.py check

80. WHY CHECKING AFTER RELOAD IS NECESSARY

Just:

systemctl reload

is not enough.

The correct logic:

      |
      v
check the syntax
      |
      v

      |
      v
obtain the effective config
      |
      v
check the values

This makes it possible to detect situations where the configuration file exists but the resulting OpenSSH policy differs from the expected one.

81. IMPORTANT LIMITATIONS

Some hardening settings reduce SSH functionality.

For example:

AllowTcpForwarding no

may disable SSH tunnels.

AllowAgentForwarding no

may disrupt Agent Forwarding.

X11Forwarding no

disables X11 forwarding.

Compression no

disables SSH compression.

Therefore, applying hardening must take the purpose of the server into account.

82. IMPORTANT FOR ADMINISTRATORS

Before applying, it is recommended to make sure that a working administrative access exists.

It is especially important to check:

  • the administrator's SSH key;
  • the administrator user;
  • the ability to log in;
  • root policy;
  • forwarding requirements;
  • the presence of a backup or second access channel.

Despite the presence of backup and rollback, the administrator must understand which SSH capabilities are used by a particular server.

92. SHORT DESCRIPTION FOR THE README

ServerGuard SSH Hardening is a Linux module for automated hardening of the OpenSSH configuration.

The module creates:

/etc/ssh/sshd_config.d/99-serverguard-hardening.conf

and applies the following restrictions:

  • prohibition of empty passwords;
  • prohibition of root password login;
  • MaxAuthTries = 3;
  • LoginGraceTime = 30;
  • disabling X11 Forwarding;
  • disabling TCP Forwarding;
  • disabling SSH Agent Forwarding;
  • disabling SSH Compression.

A backup is created before the change.

After creation, the configuration is verified via:

sshd -t

After reload, the effective configuration is verified via:

sshd -T

The module also supports:

  • backup;
  • restore;
  • emergency backup;
  • rollback;
  • verification of the effective configuration;
  • protection against Path Traversal.

93. CONCLUSION

ServerGuard SSH Hardening is a separate security layer of ServerGuard intended specifically for managing the OpenSSH policy.

The main task of the module:

not just to change the SSH configuration,

but to perform a controlled process:

1. check privileges;
2. determine the SSH service;
3. save the original configuration;
4. create the ServerGuard policy;
5. check the syntax;
6. apply the configuration;
7. check the actual values;
8. report the result;
9. perform restoration if necessary.

The main architectural diagram:

BACKUP
   ↓
CONFIGURE
   ↓
VALIDATE
   ↓
RELOAD
   ↓
VERIFY
   ↓
SUCCESS

On error:

ERROR
   ↓
ROLLBACK

Thus, SSH Hardening is not merely a set of OpenSSH parameters but an automated mechanism for managing, verifying, and restoring the SSH configuration of a Linux server.
