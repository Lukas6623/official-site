MODULE 03 / SSH HARDENING

SSH Hardening

Review and manage SSH configuration.

Модуль: SSH Hardening
Основной файл: ssh_hardening.py
Платформа: Linux / Ubuntu
Язык: Python 3
Технологии: Python, OpenSSH, systemd
Проект: ServerGuard

Назначение модуля:

Автоматизированное усиление безопасности SSH-сервера,
проверка конфигурации OpenSSH, резервное копирование,
применение контролируемой политики безопасности
и безопасное восстановление SSH-конфигурации.

1. ОБЩЕЕ ОПИСАНИЕ

SSH Hardening — серверный модуль ServerGuard, предназначенный для автоматического управления параметрами безопасности OpenSSH.

Модуль позволяет:

  • проверить права пользователя;
  • определить SSH-сервис;
  • проверить состояние SSH;
  • создать необходимые директории;
  • создать резервную копию конфигурации;
  • создать конфигурацию ServerGuard;
  • проверить конфигурацию OpenSSH;
  • применить изменения;
  • перезагрузить SSH-сервис;
  • проверить фактически применённые параметры;
  • определить состояние hardening;
  • удалить конфигурацию ServerGuard;
  • восстановить предыдущую конфигурацию;
  • выполнить rollback при ошибке.

Главная идея модуля:

ServerGuard не изменяет весь /etc/ssh/sshd_config.

Вместо этого используется отдельный конфигурационный fragment:

/etc/ssh/sshd_config.d/99-serverguard-hardening.conf

Основной файл:

/etc/ssh/sshd_config

при этом остаётся отдельным.

Такой подход позволяет ServerGuard применять собственную SSH-политику, не переписывая полностью существующую конфигурацию администратора.

2. ЧТО ТАКОЕ SSH HARDENING

Hardening — это усиление безопасности системы за счёт ограничения ненужных или потенциально опасных возможностей.

В контексте SSH это означает изменение политики OpenSSH таким образом, чтобы сервер разрешал только необходимые функции.

ServerGuard устанавливает следующие параметры:

PermitEmptyPasswords no

X11Forwarding no

AllowTcpForwarding no

AllowAgentForwarding no

MaxAuthTries 3

LoginGraceTime 30

Compression no

PermitRootLogin prohibit-password

Таким образом ограничиваются:

  • пустые пароли;
  • парольная аутентификация root;
  • количество попыток аутентификации;
  • время прохождения аутентификации;
  • X11 forwarding;
  • TCP forwarding;
  • SSH Agent Forwarding;
  • SSH compression.

3. SSH HARDENING НЕ РАВЕН BRUTE-FORCE PROTECTION

Важно разделять две задачи.

SSH Hardening отвечает за:

ПОЛИТИКУ SSH

То есть:

какие возможности разрешены;
какие возможности запрещены;
какие ограничения применяются.

Модуль Security отвечает за:

ОБНАРУЖЕНИЕ АТАК

Например:

  • анализ неудачных входов;
  • обнаружение большого количества попыток;
  • анализ IP;
  • блокировка IP;
  • защита от brute-force.

Поэтому:

SSH Hardening
    =
усиление конфигурации OpenSSH

а:

Security
    =
обнаружение и блокировка подозрительной активности.

Эти механизмы дополняют друг друга.

/etc/ssh/

8. ТРЕБОВАНИЯ К ПРАВАМ

Изменение:

/etc/ssh/

и управление SSH-сервисом требуют повышенных привилегий.

Поэтому модуль выполняет проверку root.

Используется:

os.geteuid() == 0

Если программа запущена без root:

ERROR: This script must be run as root.

Операция прекращается.

Это необходимо для работы с:

/etc/ssh/sshd_config

/etc/ssh/sshd_config.d/

/opt/serverguard/backups

и systemd.

9. ВЫПОЛНЕНИЕ LINUX-КОМАНД

Для запуска системных команд используется:

run_command(command, check=False)

Внутри используется:

subprocess.run()

Функция получает:

command

и возвращает:

returncode
stdout
stderr

Пример:

code, stdout, stderr = run_command(
    ["sshd", "-t"]
)

Если:

code == 0

команда завершилась успешно.

Если команда завершилась ошибкой, используется:

stderr

для диагностики.

Таким образом, Python-модуль не реализует собственный SSH daemon, а управляет существующим OpenSSH через стандартные Linux-команды.

10. ОБНАРУЖЕНИЕ SSH-СЕРВИСА

В Linux SSH service может называться:

ssh

или:

sshd

Поэтому модуль не должен жёстко зависеть только от одного имени.

Функция:

get_ssh_service()

определяет используемое имя сервиса.

После обнаружения результат используется при дальнейших операциях.

Например:

systemctl is-active ssh

или:

systemctl is-active sshd

Аналогично выполняется:

systemctl reload ssh

или:

systemctl reload sshd

11. ПРОВЕРКА SSH-СЕРВИСА

Функция:

check_ssh_service()

проверяет:

  • найден ли SSH service;
  • активен ли SSH service.

Используется:

systemctl is-active <service>

Если результат:

active

SSH считается работающим.

Пример:

SSH service: ACTIVE

Если сервис неактивен, его состояние выводится пользователю.

12. РЕЗЕРВНОЕ КОПИРОВАНИЕ

Изменение SSH-конфигурации является потенциально опасной операцией.

Ошибка в конфигурации может привести к тому, что новые SSH-соединения не смогут установиться.

Поэтому ServerGuard использует принцип:

BACKUP BEFORE CHANGE

Перед изменением конфигурации создаётся резервная копия.

Backup находится:

/opt/serverguard/backups

13. BACKUP ОСНОВНОЙ КОНФИГУРАЦИИ

Функция:

backup_main_config()

работает с:

/etc/ssh/sshd_config

Создаётся файл:

sshd_config_YYYYMMDD_HHMMSS.backup

Например:

sshd_config_20260930_215300.backup

Для копирования используется:

shutil.copy2()

Временная метка позволяет хранить несколько резервных копий.

14. BACKUP SERVERGUARD-КОНФИГУРАЦИИ

Если уже существует:

/etc/ssh/sshd_config.d/99-serverguard-hardening.conf

перед созданием новой версии она также может быть сохранена.

Пример:

99-serverguard-hardening_20260930_215300.backup

Таким образом можно сохранить предыдущую версию политики ServerGuard.

Важно:

основной sshd_config

и:

ServerGuard hardening config

резервируются отдельно.

15. СОЗДАНИЕ HARDENING-КОНФИГУРАЦИИ

Функция:

create_hardening_config()

создаёт:

/etc/ssh/sshd_config.d/99-serverguard-hardening.conf

В файл записывается политика ServerGuard.

Основные параметры:

PermitEmptyPasswords no

X11Forwarding no

AllowTcpForwarding no

AllowAgentForwarding no

MaxAuthTries 3

LoginGraceTime 30

Compression no

PermitRootLogin prohibit-password

После создания устанавливаются права:

0644

16. PermitEmptyPasswords

Параметр:

PermitEmptyPasswords no

запрещает использование пустого пароля при SSH-аутентификации.

Идея настройки:

пустой пароль
    |
    v
SSH authentication
    |
    v
запрещено

Это устраняет возможность использовать пустой пароль как SSH-механизм аутентификации.

17. X11Forwarding

ServerGuard устанавливает:

X11Forwarding no

X11 Forwarding позволяет передавать X11-графику через SSH.

Если сервер используется преимущественно для:

  • серверных приложений;
  • администрирования;
  • разработки;
  • фоновых сервисов;

X11 forwarding может быть не нужен.

Поэтому ServerGuard отключает эту возможность.

Важно:

SSH при этом НЕ отключается.

Отключается только X11 forwarding.

18. AllowTcpForwarding

ServerGuard устанавливает:

AllowTcpForwarding no

TCP forwarding позволяет использовать SSH для сетевого туннелирования.

Например:

клиент
   |
   | SSH
   v
сервер
   |
   v
другой сетевой ресурс

Если сервер использует SSH-туннели, отключение TCP forwarding может изменить существующий рабочий процесс.

Поэтому эту настройку необходимо учитывать перед применением hardening.

19. AllowAgentForwarding

ServerGuard устанавливает:

AllowAgentForwarding no

SSH Agent Forwarding позволяет использовать SSH-agent через удалённое соединение.

Это может быть удобно при администрировании нескольких серверов.

Если такая возможность серверу не требуется, ServerGuard её отключает.

20. MaxAuthTries

ServerGuard устанавливает:

MaxAuthTries 3

Параметр ограничивает количество попыток аутентификации в рамках одного SSH-соединения.

Важно:

MaxAuthTries 3

не означает:

"после трёх попыток IP блокируется".

Это разные механизмы.

IP-блокировка относится к отдельной системе Security.

21. LoginGraceTime

ServerGuard устанавливает:

LoginGraceTime 30

Клиент получает ограниченное время для прохождения аутентификации.

В политике ServerGuard:

30 секунд

Это уменьшает период существования неаутентифицированного соединения.

22. Compression

ServerGuard устанавливает:

Compression no

SSH compression отключается.

Это уменьшает количество доступных функций SSH, если сжатие не требуется конкретному серверу.

23. PermitRootLogin

ServerGuard устанавливает:

PermitRootLogin prohibit-password

Это означает, что парольная аутентификация root через SSH запрещается.

При этом ключевая аутентификация root может оставаться доступной, если другие настройки OpenSSH это позволяют.

Таким образом:

root + пароль
    |
    v
запрещено

root + SSH key
    |
    v
может быть разрешено

Это отличается от:

PermitRootLogin no

При:

PermitRootLogin no

root полностью запрещается через SSH.

24. ПОЧЕМУ ИСПОЛЬЗУЕТСЯ prohibit-password

ServerGuard намеренно использует:

PermitRootLogin prohibit-password

а не:

PermitRootLogin no

Это позволяет сохранить возможность административного доступа через SSH-ключ.

Итоговая возможность входа всё равно зависит от других параметров OpenSSH.

Например:

PubkeyAuthentication
PasswordAuthentication
AuthorizedKeysFile

и других настроек.

Поэтому окончательное состояние рекомендуется проверять через:

sshd -T

25. ПРОВЕРКА КОНФИГУРАЦИИ

Перед reload ServerGuard использует:

sshd -t

Команда проверяет конфигурацию OpenSSH на ошибки.

Условно:

sshd -t
   |
   +---- 0
   |      |
   |      v
   |   VALID
   |
   +---- != 0
          |
          v
       INVALID

Если конфигурация невалидна, операция применения не должна продолжаться как успешная.

26. ПОЧЕМУ sshd -t ВАЖНА

Представим:

ServerGuard
     |
     v
создаёт config
     |
     v
   sshd -t
     |
   +---+
   |   |
  OK ERROR
   |   |
   v   v
reload rollback

Таким образом, синтаксическая ошибка обнаруживается до нормального применения конфигурации.

27. RELOAD SSH

После успешной проверки выполняется:

systemctl reload <ssh-service>

Используется:

reload

а не обязательный:

restart

Это позволяет перечитать конфигурацию работающим SSH daemon.

При успешном reload модуль продолжает проверку.

28. EFFECTIVE CONFIGURATION

После применения используется:

sshd -T

Команда показывает эффективную конфигурацию OpenSSH.

Это особенно важно, потому что OpenSSH может использовать несколько конфигурационных файлов.

Например:

/etc/ssh/sshd_config

и:

/etc/ssh/sshd_config.d/*.conf

Поэтому содержимое одного файла не всегда равно итоговой конфигурации SSH daemon.

ServerGuard проверяет именно результат:

sshd -T

29. ПОЛУЧЕНИЕ ЗНАЧЕНИЙ

Функция:

get_config_value(config, name)

получает значение параметра из результата:

sshd -T

Например:

permitrootlogin prohibit-password

разбирается как:

name:
    permitrootlogin

value:
    prohibit-password

Сравнение производится без зависимости от регистра.

Если параметр отсутствует:

unknown

30. СРАВНЕНИЕ ЗНАЧЕНИЙ

Функция:

value_matches(actual, expected)

сравнивает:

фактическое значение

и:

ожидаемое значение.

Для:

prohibit-password

также может учитываться:

without-password

Это связано с различиями представления этой настройки в версиях OpenSSH.

31. ПРОВЕРКА HARDENING

Основная функция:

check_hardening()

сначала проверяет:

/etc/ssh/sshd_config.d/99-serverguard-hardening.conf

Если файла нет:

ServerGuard hardening: NOT INSTALLED

Если файл существует, выполняется:

sshd -T

После чего проверяются параметры.

32. ПРОВЕРЯЕМЫЕ ПАРАМЕТРЫ

Проверяются:

PermitRootLogin
PasswordAuthentication
PubkeyAuthentication
PermitEmptyPasswords
MaxAuthTries
LoginGraceTime
X11Forwarding
AllowTcpForwarding
AllowAgentForwarding
Compression

При этом не все параметры являются жёсткими требованиями.

33. ОБЯЗАТЕЛЬНЫЕ ПАРАМЕТРЫ

Следующие параметры должны соответствовать политике ServerGuard:

PermitRootLogin
    prohibit-password

PermitEmptyPasswords
    no

MaxAuthTries
    3

LoginGraceTime
    30

X11Forwarding
    no

AllowTcpForwarding
    no

AllowAgentForwarding
    no

Compression
    no

Если значение совпадает:

[OK]

Если отличается:

[FAIL]

34. ИНФОРМАЦИОННЫЕ ПАРАМЕТРЫ

Для:

PasswordAuthentication

и:

PubkeyAuthentication

модуль выводит фактическое значение как информацию.

То есть эти параметры показываются пользователю, но не используются как жёсткое условие успешного hardening.

Например:

[INFO] PasswordAuthentication yes

не обязательно означает ошибку.

35. РЕЗУЛЬТАТ ПРОВЕРКИ

Если все обязательные параметры соответствуют политике:

ServerGuard hardening: ENABLED

Если хотя бы один обязательный параметр отличается:

ServerGuard hardening: PARTIALLY APPLIED

Это позволяет определить разницу между:

файл существует

и:

политика реально применяется.

36. УДАЛЕНИЕ HARDENING

Функция:

remove_hardening_config()

удаляет:

/etc/ssh/sshd_config.d/99-serverguard-hardening.conf

Если файла нет, это не считается критической ошибкой.

Удаление используется, в частности, при rollback.

37. ПОЛНЫЙ ПРОЦЕСС APPLY

Команда:

ssh_hardening.py apply

запускает процесс применения hardening.

Общая последовательность:

1. Проверка root
       |
       v
2. Создание директорий
       |
       v
3. Backup sshd_config
       |
       v
4. Backup старого ServerGuard config
       |
       v
5. Создание нового config
       |
       v
6. sshd -t
       |
       +---- ERROR ---> rollback
       |
       v
7. systemctl reload
       |
       +---- ERROR ---> rollback
       |
       v
8. sshd -T
       |
       v
9. Проверка параметров
       |
       v
10. Результат

38. BACKUP ПЕРЕД APPLY

Перед изменением основного SSH-конфигурационного файла создаётся backup.

Если backup не удалось создать:

APPLY

отменяется.

Принцип:

backup failed
     |
     v
hardening cancelled

Это предотвращает изменение конфигурации без возможности вернуться к сохранённой версии.

39. ОТКАТ ПРИ ОШИБКЕ sshd -t

Если после создания ServerGuard-конфигурации:

sshd -t

возвращает ошибку:

1. ошибка выводится;
2. ServerGuard удаляет созданный hardening config;
3. операция считается неуспешной.

Схема:

CREATE
  |
  v
sshd -t
  |
  v
ERROR
  |
  v
REMOVE CONFIG
  |
  v
CANCEL

40. ОТКАТ ПРИ ОШИБКЕ RELOAD

Если:

sshd -t

успешен, но:

systemctl reload

завершается ошибкой:

1. ошибка выводится;
2. hardening config удаляется;

Модуль поддерживает восстановление основной SSH-конфигурации.

не является тем же самым, что backup основного sshd_config.

Конфигурации хранятся отдельно.

45. АВАРИЙНАЯ КОПИЯ ПЕРЕД RESTORE

Например:

Он нужен для возможности rollback, если выбранная старая конфигурация окажется невалидной.

60. БЕЗОПАСНОСТЬ МОДУЛЯ

В модуле реализованы несколько защитных механизмов.

1. ROOT CHECK

Только root может выполнять привилегированные операции.

2. BACKUP BEFORE CHANGE

Перед изменением создаётся резервная копия.

3. CONFIG VALIDATION

Используется:

sshd -t

4. EFFECTIVE CONFIG CHECK

Используется:

sshd -T

5. EMERGENCY BACKUP

Перед restore сохраняется текущая конфигурация.

6. ROLLBACK

При проблеме с восстановлением используется emergency backup.

7. PATH TRAVERSAL PROTECTION

Опасные элементы пути запрещаются.

8. BACKUP TYPE VALIDATION

Разрешаются только предусмотренные типы backup.

61. ЧТО ИМЕННО ЗАЩИЩАЕТ SSH HARDENING

Модуль изменяет политику OpenSSH.

Он ограничивает:

  • пустые пароли;
  • root password login;
  • число попыток аутентификации;
  • время аутентификации;
  • X11 forwarding;
  • TCP forwarding;
  • SSH Agent Forwarding;
  • SSH compression.

Это защита именно на уровне:

SSH daemon configuration.

62. ЧЕГО МОДУЛЬ НЕ ДЕЛАЕТ

SSH Hardening НЕ является:

  • антивирусом;
  • firewall;
  • IDS/IPS;
  • системой блокировки IP;
  • системой анализа сетевых пакетов;
  • системой мониторинга файлов;
  • системой обнаружения malware;
  • полноценной защитой от DDoS.

Он отвечает за конфигурацию OpenSSH.

Например:

MaxAuthTries 3

не означает:

"IP заблокируется после трёх попыток".

Для обнаружения и блокировки IP используется отдельная логика ServerGuard Security.

63. SSH HARDENING И SECURITY

Архитектура ServerGuard разделяет обязанности.

SSH Hardening:

OpenSSH configuration
      |
      +-- authentication limits
      +-- root login policy
      +-- forwarding
      +-- compression
      +-- empty passwords

Security:

SSH activity
      |
      +-- failed login detection
      +-- IP analysis
      +-- brute-force detection
      +-- blocking

Один модуль не заменяет другой.

64. SSH HARDENING И FIREWALL

SSH Hardening не является firewall.

Он не отвечает за:

UFW rules
packet filtering
IP blocking

Уровни можно представить так:

Internet
   |
   v
Firewall
   |
   v
SSH service
   |
   v
SSH authentication
   |
   v

Каждый уровень выполняет свою задачу.

65. ДЛЯ НАЧИНАЮЩИХ

Если объяснить модуль максимально просто:

SSH Hardening — это программа, которая говорит SSH:

"Используй более строгие правила безопасности."

Например:

означает:

ограничить количество попыток аутентификации

67. ПОЧЕМУ ИСПОЛЬЗУЕТСЯ CONFIGURATION FRAGMENT

Вместо полного изменения:

/etc/ssh/sshd_config

ServerGuard создаёт:

/etc/ssh/sshd_config.d/99-serverguard-hardening.conf

Преимущество такого подхода:

основной конфигурационный файл остаётся отдельно;

политика ServerGuard имеет собственный файл;

обновление ServerGuard не требует полного переписывания
конфигурации администратора;

rollback ServerGuard-конфигурации может выполняться отдельно.

68. ПОЧЕМУ ИСПОЛЬЗУЕТСЯ sshd -t

Команда:

является барьером перед reload.

Условно:

   |

   |    |
   |    v
   |  VALID
   |

69. ПОЧЕМУ ИСПОЛЬЗУЕТСЯ sshd -T

Команда:

sshd -T

показывает итоговую конфигурацию OpenSSH.

Это особенно важно при наличии:

/etc/ssh/sshd_config

и:

/etc/ssh/sshd_config.d/*.conf

ServerGuard проверяет не просто созданный файл, а итоговое состояние, которое видит OpenSSH.

70. ЭФФЕКТИВНАЯ КОНФИГУРАЦИЯ

Можно разделить два понятия.

CONFIGURATION FILE:

99-serverguard-hardening.conf

и:

результат sshd -T

Первое показывает:

что записал ServerGuard.

Второе показывает:

Поэтому:

81. ВАЖНЫЕ ОГРАНИЧЕНИЯ

Некоторые hardening-настройки уменьшают функциональность SSH.

Например:

AllowTcpForwarding no

может отключить SSH-туннели.

AllowAgentForwarding no

может нарушить Agent Forwarding.

X11Forwarding no

отключает X11 forwarding.

Compression no

отключает SSH compression.

Поэтому применение hardening должно учитывать назначение сервера.

82. ВАЖНО ДЛЯ АДМИНИСТРАТОРОВ

Перед применением рекомендуется убедиться, что существует рабочий административный доступ.

Особенно важно проверить:

  • SSH-ключ администратора;
  • пользователя администратора;
  • возможность входа;
  • root policy;
  • требования к forwarding;
  • наличие резервного или второго канала доступа.

Несмотря на наличие backup и rollback, администратор должен понимать, какие SSH-возможности используются конкретным сервером.

83. ОТЛИЧИЕ ОТ РУЧНОГО РЕДАКТИРОВАНИЯ

Ручной вариант:

   99-serverguard-hardening.conf

89. ЧТО ПРОВЕРЯТЬ ПРИ ПРОБЛЕМАХ

Если SSH Hardening не применяется, необходимо проверить:

  • запущен ли скрипт от root;
  • существует ли /etc/ssh/;
  • существует ли sshd;
  • найден ли systemd service;
  • доступен ли systemctl;
  • существует ли sshd_config;
  • доступна ли директория sshd_config.d;
  • проходит ли sshd -t;
  • какой результат даёт sshd -T;
  • существует ли backup;
  • не используется ли настройка, конфликтующая с политикой.

92. КРАТКОЕ ОПИСАНИЕ ДЛЯ README

ServerGuard SSH Hardening — это Linux-модуль для автоматизированного усиления конфигурации OpenSSH.

Модуль создаёт:

/etc/ssh/sshd_config.d/99-serverguard-hardening.conf

и применяет следующие ограничения:

  • запрет пустых паролей;
  • запрет парольного входа root;
  • MaxAuthTries = 3;
  • LoginGraceTime = 30;
  • отключение X11 Forwarding;
  • отключение TCP Forwarding;
  • отключение SSH Agent Forwarding;
  • отключение SSH Compression.

Перед изменением создаётся резервная копия.

После создания конфигурация проверяется через:

sshd -t

После reload проверяется эффективная конфигурация через:

sshd -T

Модуль также поддерживает:

  • backup;
  • restore;
  • emergency backup;
  • rollback;
  • проверку effective configuration;
  • защиту от Path Traversal.

93. ИТОГ

ServerGuard SSH Hardening является отдельным уровнем безопасности ServerGuard, предназначенным непосредственно для управления политикой OpenSSH.

Основная задача модуля:

не просто изменить SSH-конфигурацию,

а выполнить контролируемый процесс:

1. проверить права;
2. определить SSH service;
3. сохранить исходную конфигурацию;
4. создать ServerGuard policy;
5. проверить синтаксис;
6. применить конфигурацию;
7. проверить фактические значения;
8. сообщить результат;
9. при необходимости выполнить восстановление.

Главная архитектурная схема:

BACKUP
   ↓
CONFIGURE
   ↓
VALIDATE
   ↓
RELOAD
   ↓
VERIFY
   ↓
SUCCESS

При ошибке:

ERROR
   ↓
ROLLBACK

Таким образом SSH Hardening представляет собой не просто набор параметров OpenSSH, а автоматизированный механизм управления, проверки и восстановления SSH-конфигурации Linux-сервера.
