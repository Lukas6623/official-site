SSH Key Setup

Learn how to create an SSH key, install the public key on your Linux server and connect to the server using ServerGuard.

1. Overview

ServerGuard can authenticate with Linux servers using an SSH private key instead of an account password.

SSH key authentication uses a pair of cryptographic keys: a private key stored on your computer and a public key installed on the Linux server.

The private key stays on your computer. Only the public key should be installed on the server.

2. Requirements

Before starting, make sure you have:

  • Windows 10 or Windows 11.
  • OpenSSH Client installed on Windows.
  • Access to a Linux server.
  • The server IP address or hostname.
  • A Linux account that can log in through SSH.
  • The account password for the initial key installation.

3. Create an SSH key

Open PowerShell on Windows.

Check that OpenSSH is available: 

ssh -V

Create an Ed25519 SSH key: 

ssh-keygen -t ed25519

When Windows asks where to save the key, press Enter to use the default location.

The default location is: 

C:\Users\YOUR_USERNAME\.ssh\id_ed25519

You will then be asked to enter a passphrase. You can leave it empty or use an additional passphrase to protect the private key.

4. Private and public keys

After creating the key, Windows normally creates two files:

Private key id_ed25519

Must remain private and should never be uploaded to the server or shared with other people.

Public key id_ed25519.pub

This key can be installed on the Linux server.

To display your public key: 

Get-Content "$env:USERPROFILE\.ssh\id_ed25519.pub"

The output should look similar to: 

ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA... ServerGuard

5. Install the public key on the Linux server

First connect to your Linux server using the normal SSH password: 

ssh root@SERVER_IP

Replace SERVER_IP with the address of your server.

Create the SSH directory: 

mkdir -p ~/.ssh
chmod 700 ~/.ssh

Open the authorized keys file: 

nano ~/.ssh/authorized_keys

Paste the complete contents of your id_ed25519.pub file into this file.

Each public key must occupy its own line.

Save the file in nano: 

Ctrl + O
Enter
Ctrl + X

6. Configure SSH key permissions

Set the recommended permissions: 

chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys

You can verify the file: 

ls -la ~/.ssh

The authorized_keys file should not be writable by other users.

7. Test SSH key authentication

Exit the current SSH session: 

exit

From Windows, connect using the private key: 

ssh -i "$env:USERPROFILE\.ssh\id_ed25519" root@SERVER_IP

If the key has no passphrase and everything is configured correctly, the Linux account password should not be requested.

If your SSH key has a passphrase, SSH may ask for the passphrase protecting the private key. This is different from the Linux account password.

8. Test password authentication

You can test password authentication without deleting the SSH key.

Use: 

ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password root@SERVER_IP

SSH will attempt password authentication for this connection only.

This command does not remove or modify your SSH key. It only tells the SSH client not to use public-key authentication for this connection.

9. Connect to the server using ServerGuard

Start ServerGuard and create or edit a server connection.

Enter the normal server connection information:

  • Server IP address or hostname.
  • SSH port, normally 22.
  • Linux username.

For authentication, select: 

Auth: Private key

Select your private key. For example: 

C:\Users\YOUR_USERNAME\.ssh\id_ed25519

If the private key has a passphrase, enter it in the corresponding field.

SERVERGUARD / CONNECTION

Authentication method

Select Private key instead of password authentication.

SERVERGUARD / KEY

Private key path

Select the private key stored on your Windows computer. 

C:\Users\YOUR_USERNAME\.ssh\id_ed25519
SERVERGUARD / AUTHENTICATION

Verify the connection

After connecting, ServerGuard should indicate that the server was authenticated using the private key.

10. SSH key passphrase

A passphrase is an additional password that protects the private key file.

There are two different credentials:

  • Linux password — password of the server account.
  • SSH key passphrase — protects the private key on your computer.

If the private key was created without a passphrase, leave the ServerGuard key passphrase field empty.

11. SSH Hardening

SSH key authentication is especially important when using ServerGuard SSH Hardening.

Hardening can change SSH authentication settings. Losing access to a server after changing SSH settings can be difficult to recover from.

ServerGuard therefore checks the authentication method before applying SSH Hardening.

ServerGuard allows SSH Hardening to continue when the current ServerGuard connection uses SSH public-key authentication.
If ServerGuard is connected using password authentication, SSH Hardening is blocked for safety. This prevents password authentication from being disabled while the current connection depends on that password.

Before using SSH Hardening, make sure that:

  1. The public key is installed on the server.
  2. SSH key authentication works.
  3. ServerGuard is connected using Private key.
  4. You can reconnect to the server using the private key.

12. Troubleshooting

Permission denied (publickey)

Check that the public key is present: 

cat ~/.ssh/authorized_keys

Check the permissions: 

chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys

Check whether public-key authentication is enabled: 

sshd -T | grep pubkeyauthentication

The expected result is: 

pubkeyauthentication yes

ServerGuard cannot authenticate using the key

Verify that the selected key is the private key: 

id_ed25519

Do not select: 

id_ed25519.pub

The .pub file is the public key and should not be used as the private key in ServerGuard.

SSH asks for a password

Test the connection manually: 

ssh -v -i "$env:USERPROFILE\.ssh\id_ed25519" root@SERVER_IP

The verbose output can show whether the client is actually attempting to use the selected key.

Test the key with maximum SSH debugging 

ssh -vvv -i "$env:USERPROFILE\.ssh\id_ed25519" root@SERVER_IP

13. Security recommendations

Protect your private SSH key carefully.

  • Never publish the private key.
  • Never upload the private key to GitHub.
  • Never send the private key through Telegram, email or other messaging services.
  • Do not copy the private key to the Linux server unless there is a specific security reason.
  • Consider using a passphrase to protect important private keys.
  • Keep a secure backup of important keys.
If someone obtains your private SSH key and can use it, they may be able to authenticate to servers where the corresponding public key is authorized. Treat a leaked private key as compromised and replace it.

Summary

The complete ServerGuard SSH key workflow is: 

Windows
   │
   ├── id_ed25519
   │      └── Private key
   │
   └── id_ed25519.pub
          │
          ▼
Linux Server
   │
   └── ~/.ssh/authorized_keys
          │
          ▼
SSH key authentication
          │
          ▼
ServerGuard
   │
   └── Auth: Private key
          │
          ▼
SSH Hardening and server management

Once key authentication has been tested successfully, ServerGuard can use the private key to establish a secure SSH connection to the Linux server.
